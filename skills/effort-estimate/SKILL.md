# 工数見積もり（effort-estimate）

既存リポジトリに対する改修・機能追加の工数を、決まった手順で算出する。

## このスキルの考え方

AIに直接「何時間か」を考えさせると、分解の粒度や含める範囲が毎回変わり、結果がブレる。そこで役割を分ける。

- **Claude がやること**：コード調査、タスク分解、各タスクを基準表の「作業種別 × サイズ」に分類、補正係数の判定、根拠の記録
- **スクリプトがやること**：時間の計算（`scripts/calc.py`）

Claude は合計時間を自分で計算したり、計算結果を感覚で調整したりしない。結果が直感とズレると感じたら、数字ではなく**分類や係数の判断を見直し**、それでも違和感が残る場合は「見積もり者コメント」に書く。こうしておくと、ズレの原因が基準表にあるのか判断にあるのかを後から検証できる。

出力する数字は2種類ある。

- **実作業見込み**：人間がAI支援ありで作業した場合の実際の時間。スケジュールとアサインに使う。
- **対外工数**：先方に提示する工数。従来基準（AI支援なし）で算出する。請負（固定額）の見積もりで提示するための数字で、稼働時間で精算する契約の請求時間には使わない。ユーザーがそのような用途で使おうとしている場合は、この点を伝える。

## 手順

### 1. 依頼内容を整理する

ユーザーの指示から、改修の目的、対象機能、期待する結果を整理する。

スピード重視の運用なので、不明点があっても原則として作業を止めない。妥当な前提を置いて見積もりを進め、置いた前提は「前提条件」に、先方に確認すべきことは「先方への確認事項」に必ず書く。ただし、改修の対象自体が特定できない、複数の解釈で工数が大きく変わる（例：2倍以上）といった場合は、調査の前にユーザーに1回だけ質問する。

アプリ側・インフラ側など担当を分けて見積もる場合は、本番環境での作業（本番DBでの確認・SQL実行、手動でのタスク実行、本番へのデプロイ）を誰が実行できるかを最初に整理し、「前提条件」に書く。分からない場合は、本番へのアクセス権を持つ側が実行する前提を置く。

### 2. リポジトリを調査する

影響範囲を実際のコードで確認する。推測で済ませず、該当ファイルを開いて確かめる。主に見るところ：

- ルーティング、コントローラ、リクエスト（バリデーション）
- サービス・モデル・リポジトリなどのビジネスロジック
- マイグレーション、テーブル定義、既存データへの影響
- フロントエンド（画面、コンポーネント、API呼び出し）
- 既存テストの有無と構成（テストを追加・修正する範囲の判断に使う）
- 同じ機能を呼び出している他の箇所（回帰確認の範囲の判断に使う）

調査で確認したファイルパスは、タスクごとの「根拠」として記録する。

### 3. タスクを分解して分類する

`references/estimation_rules.json` の作業種別一覧と、`references/classification_guide.md` のサイズ判定基準を読んでから分解する。分解した結果は手順5で tasks.json に書く。項目の書き方は `references/tasks_schema.md` にある。

- 各タスクは必ず作業種別（`type`）とサイズ（`S` / `M` / `L`）に当てはめる。
- L を超えるタスクは、複数のタスクに分割する。
- 以下の工程は、どの案件でも必ず検討する。不要と判断した工程は、tasks.json の `skipped_phases` に理由を書き、同じ理由を「前提条件」にも書く。
  - 調査・設計（既存コード調査、先方との仕様確認）
  - テスト（自動テスト、手動の動作確認、回帰確認）
  - レビュー・修正
  - リリース・本番確認
- どの作業種別にも当てはまらない作業だけ、`type: "custom"` とし、工程（`phase`）、三点見積もり（楽観・標準・悲観）、理由を付ける。custom は計算上ブレの原因になるので、できるだけ既存の種別に寄せる。custom が繰り返し出る作業は、基準表に追加すべき候補としてコメントに書く。
- 担当を分けて見積もる場合、同じ作業を両方に計上しない。作業を実行する側に計上し、依頼・確認するだけの側は、結果の確認として小さく計上するか、他のタスクに含める。
- 溜まっているデータを初回にまとめて処理するなど、一度だけの作業（初回の手動実行、移行、事前のバックアップ）は、リスク欄に書くだけでなくタスクとして計上する。

### 4. 補正係数を判定する

タスクごとに、`classification_guide.md` の基準で次の3つを判定する。

- `uncertainty`（仕様の不確実性）：`low` / `mid` / `high`
- `complexity`（既存コードの複雑さ）：`low` / `mid` / `high`
- `unfamiliarity`（未経験の技術・領域）：`none` / `partial` / `new`

案件全体のリスク（`project_risk`：`low` / `mid` / `high`）も判定する。これはバッファ率に使う。バッファは実作業見込みの小計にバッファ率をかけて算出し、同じ時間を対外工数にも「保険」としてそのまま載せる（対外工数の小計には率をかけない）。想定外の作業に実際に対応するのは AI 支援ありの体制なので、必要になる予備の時間は実作業見込みと同じ、という考え方による。

### 5. 保存先を決め、tasks.json を作成して計算する

まず保存先を決める。対応内容は、ファイル名を見て何の対応かわかる短い日本語にする（例：「注文一覧のステータス絞り込みとCSV出力」）。

```bash
python3 <このスキルのディレクトリ>/scripts/output_path.py "<対応内容>"
python3 <このスキルのディレクトリ>/scripts/output_path.py "<対応内容>" --dir "<保存先フォルダ>"   # 保存先を指定する場合
```

1行目が見積もり結果（.md）、2行目が tasks.json の保存先になる。同名ファイルがある場合は連番が付き、過去の見積もりは上書きされない。

保存先のフォルダは次の順で決まる。

1. ユーザーが保存先を指定した場合は、`--dir` でそのフォルダを渡す。
2. 環境変数 `EFFORT_ESTIMATE_OUTPUT_DIR` が設定されていれば、そのフォルダになる（スクリプトが自動で読むので、何も渡さなくてよい）。
3. どちらもなければ、Git リポジトリと同じ階層の `docs/` フォルダになる。リポジトリの外なので、リポジトリを汚さない。

Git リポジトリの外で実行すると、3 の保存先を決められずエラーになる。その場合は保存先をユーザーに確認し、`--dir` を付けて実行し直す。リポジトリの中のフォルダを指定された場合は、見積もりのファイルが `git status` に出ることをユーザーに伝える。

**パスの扱い（出力先を間違えないために）**：出力された2つのパスは、毎回そのまま絶対パスとしてコピーして使う。シェル変数に入れて文字列をつなぐこと（例：`$O_アプリ.md`）はしない。zsh は日本語も変数名の一部とみなすため、`$O_アプリ` は未定義の変数として空文字に展開される。その結果、カレントディレクトリ（リポジトリ直下）に `.md` という名前のファイルができてしまう。アプリ側とインフラ側など、見積もりを複数に分ける場合は、それぞれ output_path.py を実行して別のパスを取得する。

次に、`references/tasks_schema.md` の形式で tasks.json を2行目のパスにファイル作成ツール（Claude Code では Write）で作成し、計算する。記入例は `assets/example_tasks.json` と `assets/example_tasks_custom.json` にある。tasks.json は、基準表を更新したあとに再計算したり、実績と比べたりするために残しておく（削除しない）。

```bash
python3 <このスキルのディレクトリ>/scripts/calc.py <tasks.json のパス>
```

スクリプトがエラーを出した場合は、表示された内容に従って tasks.json を直し、計算し直す。警告を出した場合（必須工程の欠落、根拠の空欄、custom の比率が高いなど）は、内容を確認し、必要なら分解をやり直す。

### 6. 結果を出力・保存する

`templates/output.md` の構成で見積もり結果を作成し、手順5で決めた .md のパスに**ファイル作成ツール**（Claude Code では Write）で保存する（シェルのヒアドキュメントやリダイレクトでは保存しない）。数値の表はスクリプトの出力をそのまま使い、書き換えない。冒頭の「対象」には、見積もった時点のリポジトリ名・ブランチ・コミット（`git rev-parse --short HEAD`）を書く。Git リポジトリでない場合は「対象」の行を省く。調査結果、前提条件、リスク、確認事項、スコープ外は Claude が文章で埋める。

保存したら、次の2点を確認する。

```bash
ls -la "<.md のパス>" "<tasks.json のパス>"   # 決めた保存先に保存されていること
git status --short                           # リポジトリに意図しないファイルが増えていないこと
```

`git status` に見積もりの作業で作ったファイルが出てきた場合は、ユーザーに報告する（ユーザーがリポジトリの中を保存先に指定した場合を除く）。Git リポジトリでない場合、`git status` の確認は省く。

確認が済んだら、チャットには工数サマリ（実作業見込み・対外工数の合計）、先方への確認事項、保存したファイルのパスを短く伝える。全文はファイルで確認してもらう。

## 補足

- 基準表の数値（`estimation_rules.json`）はチームの実績に合わせて調整していく前提のもの。数値に疑問があっても、見積もり中に勝手に書き換えない。
- 1人で作業する前提で計算する。複数人で並行する場合も、工数は合計時間で出す。
